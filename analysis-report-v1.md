# 2. Critical Risks

- CRITICAL: Public table/order/invoice access is broad and depends mainly on client-side filtering. RLS allows public `tables` select using `true` at `database/rls_policies.sql:102`, public `orders` select using `true` at `database/rls_policies.sql:172`, and public `order_items` select using `true` at `database/rls_policies.sql:200`. `/api/invoices/table` uses `supabaseAdmin` and accepts only `tableId` in `src/app/api/invoices/table/route.ts:4`, `src/app/api/invoices/table/route.ts:14`, and `src/app/api/invoices/table/route.ts:30`, so possession or guessing of a table UUID can expose sent unpaid invoices. Additive fix: introduce signed QR/table session tokens and table-scoped validation while continuing to accept legacy table IDs as a fallback during migration.
- CRITICAL: Customer order creation is not atomic. `StickyCart` inserts an `orders` row first at `src/components/menu/StickyCart.tsx:30`, then inserts `order_items` at `src/components/menu/StickyCart.tsx:55`; if item insertion fails, an empty pending order remains. Notifications compensate with retries in `src/components/dashboard/OrderNotifications.tsx:100`, but billing explicitly rejects orders without billable items in `src/app/api/invoices/route.ts:56`. Additive fix: add an RPC or API endpoint that creates order and items in one transaction, while keeping the existing direct client path as a temporary fallback.
- HIGH: Invoice generation has duplicate numbering logic and race exposure. The DB trigger generates invoice numbers in `database/schema.sql:223` and `database/schema.sql:241`, while the API also generates `invoice_number` in `src/app/api/invoices/route.ts:29` and sends it during insert at `src/app/api/invoices/route.ts:94`. Concurrent creates can still collide with `UNIQUE(restaurant_id, invoice_number)` at `database/schema.sql:135`. Additive fix: centralize numbering in one DB function that uses locking or a sequence, leaving the API response shape unchanged.
- HIGH: `GET /api/invoices` mutates data by reconciling completed orders in `src/app/api/invoices/route.ts:110` and `src/app/api/invoices/route.ts:166`. Billing loads unpaid and paid pages concurrently from `src/app/(dashboard)/dashboard/billing/page.tsx:136` and `src/app/(dashboard)/dashboard/billing/page.tsx:137`, so reads can trigger invoice creation twice under load. Additive fix: keep read reconciliation for backward compatibility but add idempotent DB constraints/transactional upsert and move proactive reconciliation to explicit completion or background paths.
- HIGH: `invoices.notes` is overloaded as customer delivery state. Staff send updates `notes: 'sent_to_table'` in `src/app/api/invoices/send/route.ts:64`; customer acknowledgement updates `notes: 'acknowledged_by_table'` in `src/app/api/invoices/table/route.ts:77`; billing detail also exposes `notes` as a general invoice field through the `Invoice` type at `src/types/index.ts:130`. Additive fix: add separate nullable columns such as `sent_to_table_at` and `acknowledged_by_table_at`, then continue reading legacy `notes` values until migrated.
- MEDIUM: Realtime and polling overlap without a single refresh coordinator. Dashboard overview listens to `order_items` changes at `src/components/dashboard/DashboardOverview.tsx:136`, uses `useRealtimeOrders` at `src/components/dashboard/DashboardOverview.tsx:157`, and also polls every 15 seconds at `src/components/dashboard/DashboardOverview.tsx:150`. Customer invoice prompts poll every 5 seconds at `src/components/menu/TableInvoice.tsx:43`. Additive fix: keep polling as fallback, but debounce realtime-triggered refreshes and pause polling when realtime is healthy.
- MEDIUM: Menu availability is enforced in UI, not in ordering. Public menu data includes all `menu_items` at `src/app/menu/[restaurantSlug]/page.tsx:78`; `MenuItemCard` disables unavailable items at `src/components/menu/MenuItemCard.tsx:51`, but `StickyCart` inserts any cart item IDs it holds at `src/components/menu/StickyCart.tsx:55`. Additive fix: validate item availability server-side in the future transactional order endpoint while keeping the client disabled state.
- LOW: Dashboard and orders duplicate table-grouping logic in `src/components/dashboard/DashboardOverview.tsx:50` and `src/app/(dashboard)/dashboard/orders/page.tsx:55`. Additive fix: extract a shared helper after behavior is covered by tests; do not change grouping output shape during the refactor.

# 5. Realtime & Polling Map

- `useRealtimeOrders` subscribes to all `orders` changes filtered by `restaurant_id` in `src/hooks/useRealtime.ts:34`. It is consumed by the orders page at `src/app/(dashboard)/dashboard/orders/page.tsx:216` and dashboard overview at `src/components/dashboard/DashboardOverview.tsx:157`.
- `useOrderStatus` subscribes to `orders` updates filtered by `id` in `src/hooks/useRealtime.ts:73`. It is consumed by customer order tracking in `src/components/menu/OrderTracker.tsx:31`.
- Dashboard overview subscribes separately to `order_items` changes in `src/components/dashboard/DashboardOverview.tsx:136` because `orders.total_amount` is updated by the DB trigger in `database/schema.sql:219`. It also polls `fetchOverview(false)` every 15 seconds at `src/components/dashboard/DashboardOverview.tsx:150`. This overlaps with `useRealtimeOrders` and can cause duplicate refreshes for one customer order.
- Staff notifications subscribe to `orders` inserts in `src/components/dashboard/OrderNotifications.tsx:82`; after an insert, they refetch the order and items up to three times in `src/components/dashboard/OrderNotifications.tsx:100` because `order_items` may not exist yet. This overlaps with the order list realtime subscription but has a distinct notification purpose.
- Billing subscribes to `invoices` changes filtered by `restaurant_id` in `src/app/(dashboard)/dashboard/billing/page.tsx:169` and refetches unpaid/paid pages through `/api/invoices`. Because `GET /api/invoices` performs reconciliation, realtime refresh can indirectly create missing invoices.
- Customer table invoices use polling only: `TableInvoice` calls `/api/invoices/table` immediately and every 5 seconds in `src/components/menu/TableInvoice.tsx:43`. There is no customer-facing invoice realtime subscription; polling is the current fallback and should not be removed without an equivalent realtime-plus-polling degradation path.

# 6. Recommended Fix Order

1. Add safety tests and observability around existing behavior before refactoring: order creation with item insert failure, completed-order invoice creation, invoice send/acknowledge, table QR flow, customer active-order tracking, dashboard realtime refresh, and billing list pagination. Keep all current endpoints and response fields.
2. Introduce an additive transactional order creation RPC/API that validates table, restaurant, menu item availability, quantities, and prices, then inserts `orders` and `order_items` atomically. Keep `StickyCart` direct Supabase creation as a compatibility fallback until the new path is proven.
3. Harden customer table access additively with signed QR/table session tokens. Continue accepting existing `tableId` flows during migration, but prefer token validation in `/api/invoices/table` and future order APIs.
4. Make invoice creation idempotent in the database: centralize invoice number generation, use locking/sequence-backed numbering, and enforce one invoice per billable order if that is the product rule. Keep `POST /api/invoices` and `GET /api/invoices` response shapes stable.
5. Replace `invoices.notes` state flags with explicit nullable columns while supporting legacy `sent_to_table` and `acknowledged_by_table` reads. Update send/table APIs to write both old and new fields during migration.
6. Add a realtime refresh coordinator/debounce for dashboard and billing. Preserve polling as a fallback; only reduce polling frequency when a healthy realtime subscription is confirmed.
7. Extract shared, behavior-preserving helpers for table grouping, service-request filtering, and invoice/order type guards after tests are in place. Avoid removing direct APIs, realtime subscriptions, polling, fields, or endpoints until fallback compatibility is verified.
